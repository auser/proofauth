What is payment-api?

        

          
It is the application service that owns the payment operation and the consumer named by the request's recipient. Priya's client reaches it over a normal network connection and submits the hex bundle; the exact JSON request shown above is embedded inside that bundle.

          
Offline describes what happens after the bundle arrives. payment-api verifies it using the bundled proof, a locally provisioned signed registry and pinned root key, and its replay cache. It does not call Acme's issuer, a registry server, or a revocation server while making the authorization decision. It may still read its own payment data and carry out the approved operation.

Security boundary
Properties and limitations

          
ProofAuth proves a cryptographic authorization statement relative to trusted inputs. It does not turn an issuer's claim into an external fact.

        

        

          

            
It proves

            
    
              
  • A trusted issuer signed Priya's identity commitment.
    • 
              
  • Priya's subject key signed this recipient-bound presentation.
    • 
              
  • The disclosed role satisfies the local scoped policy.
    • 
              
  • The registry, revocation state, lifetime, and replay checks pass.
    • 
            

          

          

            
It does not prove

            
    
              
  • That Acme's real-world identity claim was truthful.
    • 
              
  • That private keys were protected before or after signing.
    • 
              
  • That an offline revocation snapshot is newer than the consumer's copy.
    • 
              
  • Confidentiality or zero-knowledge disclosure; hex is an encoding, not encryption.
    •
